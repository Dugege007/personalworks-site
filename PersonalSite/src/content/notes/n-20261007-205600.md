# A* 寻路：一边算走了多远，一边估还剩多远

A* 是 1968 年 Hart、Nilsson、Raphael 提出的寻路算法，至今仍是 Unity NavMesh 等引擎的核心。数字孪生里 AGV、叉车、巡检机器人在车间规划路线，底层也常常是它或它的变种。

建议先打开 Red Blob Games 的 [A* 交互图解](https://www.redblobgames.com/pathfinding/a-star/introduction.html)，可以拖动起点、终点、开墙洞，亲眼看搜索范围怎么一圈圈往外扩。下面的文字配着那几张动画看会快很多。

## 它是什么

A* 解决的问题是：在一张图上，从起点到终点，找总代价最小的路径。

这里的"图"是数学意义上的图：一堆节点，加上节点之间带代价的边。A* 不知道什么是房间、门、货架、产线，它只看到节点和边。车间栅格的每个格子可以是节点，NavMesh 的每个凸多边形也可以是节点；"代价"可以是距离、时间，也可以是"这条通道有多堵"。

## 怎么工作：从洪水填充一步步改到 A*

所有这类搜索都维护一个"前沿"（frontier），也就是已经看到、还没展开的那一圈节点。每轮从前沿里取一个节点，看它的邻居，把没去过（或找到了更便宜走法）的邻居放进前沿，同时记下"它是从哪儿来的"。到终点后顺着这些"从哪儿来"往回走，就得到路径。

区别只在于每轮先取哪个节点：

1. **广度优先（BFS）**：先进先出，前沿像水波一样均匀往外扩。每步代价都一样时能找到最短路。
2. **Dijkstra**：每步代价不同（草地 1、沼泽 10）时，改用优先队列，每次取"从起点到这里实际花费 g(n)"最小的节点。能保证最短，但它往四面八方一视同仁地扩，大量时间花在背对终点的方向上。
3. **贪心最佳优先**：反过来，只按"估计离终点还有多远 h(n)"排序。空旷地图上直奔终点，非常快；但遇到 U 形障碍会一头扎进死胡同，找到的路不一定最短。
4. **A***：把两者加起来，按 f(n) = g(n) + h(n) 排序。

f(n) 的意思是：如果从起点经过 n 再到终点，总代价大概是多少。A* 每次展开"看起来总代价最低"的节点。

用等高线来想：Dijkstra 的搜索范围是以起点为圆心的一圈圈圆；A* 的搜索范围被拉成朝终点方向伸长的椭圆。终点越明确、障碍越少，椭圆越细。

代码和 Dijkstra 只差一行，入队的优先级从 `new_cost` 变成 `new_cost + heuristic(goal, next)`。

## 启发函数 h(n)：决定 A* 快不快、准不准

**不高估就保证最短。** 只要 h(n) 永远不大于 n 到终点的真实最小代价（叫"可采纳"，admissible），A* 找到的就一定是最短路。再强一点的条件叫"一致"（consistent）：对每条边 n→n'，h(n) ≤ cost(n, n') + h(n')。满足一致性时，每个节点最多被正式展开一次，实现最简单。网格上常用的几个距离启发都满足一致性。

**h 是一个旋钮**（Amit Patel 的 [启发函数笔记](http://theory.stanford.edu/~amitp/GameProgramming/Heuristics.html) 讲得最透）：

- h = 0：A* 退化成 Dijkstra，最短但最慢。
- h 越接近真实剩余代价：展开的节点越少，越快，并且仍然最短。
- h 恰好等于真实剩余代价：A* 只沿最优路走，几乎不展开别的节点。
- h 有时高估：不再保证最短，但更快。
- h 远大于 g：退化成贪心最佳优先。

**按移动规则选距离：**

- 4 方向网格用曼哈顿距离：`D * (dx + dy)`
- 8 方向网格用对角距离（D=1、D2=√2 时叫 octile）：`D * (dx + dy) + (D2 - 2*D) * min(dx, dy)`
- 任意角度移动用欧氏距离，但它比网格上的真实路径短，会让 A* 多展开一些节点。
- **不要用距离的平方省开方。** 平方和 g 不在一个量级，路一长就严重高估，A* 会退化成贪心。

**单位必须一致。** f = g + h 是加法，g 用秒、h 用米，就等于随手给 h 乘了个系数。D 应取"走一格的最小代价"，比如每格最少 4 分钟，h 就返回"格数 × 4 分钟"。

**平局打破。** 空旷网格上很多路径一样长，f 值大量相同，A* 会把它们都探一遍。常见做法是把 h 乘上 (1 + p)，p 取一个很小的数，比如 1/1000，满足 p 小于"单步最小代价 / 预期最长路径步数"。这样 A* 会偏向离终点更近的节点。这会轻微破坏可采纳性，但游戏里几乎感觉不到。

## 复杂度与代价

- 时间：最坏情况和 Dijkstra 一样，用二叉堆时是 O((V + E) log V)，V 是节点数，E 是边数。实际展开多少节点取决于 h 有多准：h 越准，展开越少。
- 空间：要存 `g`、`came_from` 和优先队列，最坏 O(V)。大地图上 A* 先撞到的往往是内存，不是 CPU。
- 最有效的提速通常不是改算法，而是让图变小：栅格换成路点图或 NavMesh，或者分层（先在粗图上找大方向，再在细图上细化）。

## 实例一：车间 AGV 绕开拥堵通道

一张 10×20 的车间栅格：`.` 是普通通道（代价 1），`~` 是拥堵通道（代价 3，比如那段经常有人工搬运），`#` 是设备和货架。AGV 可以 8 方向走，斜走代价 √2，不许斜着切过设备的角。代价 = 走的距离 × 区域系数。

完整代码见交付包 `code/2026-10-07-astar_agv.py`，核心如下：

```python
def octile(a, b):  # 8 方向网格的标准启发，最小单格代价=1，不会高估
    dx, dy = abs(a[0] - b[0]), abs(a[1] - b[1])
    return (dx + dy) + (math.sqrt(2) - 2) * min(dx, dy)

def astar(start, goal, h, w=1.0):
    frontier = [(0.0, start)]
    g = {start: 0.0}; came = {start: None}; expanded = 0
    while frontier:
        _, cur = heapq.heappop(frontier)
        expanded += 1
        if cur == goal: break
        for nxt, c in neighbors(cur):           # c = 距离 × 区域代价
            ng = g[cur] + c
            if nxt not in g or ng < g[nxt]:
                g[nxt] = ng; came[nxt] = cur
                heapq.heappush(frontier, (ng + w * h(nxt, goal), nxt))
    path, p = [], goal
    while p is not None: path.append(p); p = came[p]
    return path[::-1], g[goal], expanded
```

实际跑出来的结果（出队次数包含同一格被更便宜路径更新后留下的旧条目）：

| 方法 | 路径代价 | 出队次数 |
|---|---|---|
| Dijkstra（h = 0） | 30.97 | 187 |
| A*（octile） | 30.97 | 135 |
| 加权 A*（h × 2） | 30.97 | 53 |

中间那堵墙只有拥堵区能穿过去，所以 AGV 只斜穿了 3 格拥堵区就出来了，没有在里面多绕。三种方法代价相同，但 A* 少出队约 28%，加权 A* 少了约 72%。

加权 A* 在这张图上碰巧也拿到了最优解，这不是必然的。经典结论是：h 一致时，把 h 乘 w 得到的路径代价不超过最优解的 w 倍。仿真里 AGV 数量多、要每帧重算时，用 w = 1.2 到 2 换速度，往往是划算的。

放进数字孪生时，拥堵系数可以不写死：把昨天讲的 WIP 残差或实时占用率接进来，按区域动态改代价，路线就会跟着现场的拥堵情况变。

## 实例二：Unity NavMesh 为什么要求区域代价不小于 1

Unity 官方文档（[导航内部原理](https://docs.unity3d.com/Packages/com.unity.ai.navigation@2.0/manual/NavInnerWorkings.html)、[区域与代价](https://docs.unity3d.com/Packages/com.unity.ai.navigation@2.0/manual/AreasAndCosts.html)）写得很清楚：NavMesh 把可走区域存成凸多边形，先把起点和终点映射到最近的多边形，再用 A* 在多边形之间搜索，得到的多边形序列叫"走廊"（corridor），角色每次朝走廊里下一个可见拐角走。两节点间的代价 = 距离 × 区域代价，文档还特别写了：A* 要求所有代价都大于等于 1.0。

用上面讲的"不高估"就能解释这一点（这是我的推断，文档没写原因）：如果启发函数按"直线距离 × 1"估剩余代价，而某个区域代价是 0.5，真实代价就可能比估计还小，h 变成高估，A* 不再保证最短。把代价下限卡在 1，直线距离就永远是下界。

文档还提到一个现象：大片空地旁边有小障碍时，NavMesh 会生成一大一小的多边形，节点在大多边形里的位置不够准，A* 找到的路看起来像绕远。原因不在 A*，而在图的建法。这正对应 Red Blob 反复强调的一点：A* 只看到你给它的图。

## 应用场景

- 游戏：RTS 单位移动、RPG 寻路、塔防（塔防更常用一次 BFS 从终点反推出"流场"，所有怪共用）。
- 产线仿真：AGV、叉车、人员路径；拥堵和禁行区作为代价或障碍。
- 机器人与自动驾驶：栅格地图上的全局规划，局部再交给避障。
- 非地图问题：任何"状态 + 动作 + 代价"的问题都能套，比如拼图求解、排程中的状态空间搜索。h 要按问题专门设计。

## 局限与延伸思考

A* 只管一个智能体在静态图上的一次查询。下面这些它本身不处理，也是后面可以单独展开的题目：

- 多台 AGV 互相让路、不撞车：多智能体路径规划（MAPF），代表算法是 CBS（基于冲突的搜索）。
- 地图会变（临时堆货、设备检修）：增量重规划，代表是 D* Lite。
- 大网格提速：跳点搜索（JPS）、分层寻路（HPA*）。
- 路径平滑、转弯半径、车体尺寸：后处理和运动规划。
