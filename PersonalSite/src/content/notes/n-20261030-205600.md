# 最短列瀑布流

个人站图墙若按编号轮流进列（第 \(i\) 张进第 \(i \bmod k\) 列），横幅与纵幅混在一起时，个别列会被纵幅撑得很长。SEED=**42**、**30** 张、宽高比在 \(9/16\) 到 \(16/9\) 之间均匀抽样的对照里：三列时 round-robin 的列高差（`height_spread`）约 **338.82**，最短列贪心约 **111.93**；四列时约 **732.64** 对 **136.83**。按卡片顶边从上到下（同高再按左到右）扫编号，最短列在 2／3／4 列下逆序对都是 **0**、Kendall \(\tau=\)**1.0**；round-robin 四列逆序对 **38**、\(\tau\approx\)**0.8253**。读完可以按脚本复现这两套指标，弄清「下一张进当前最矮列、并列取最左」在做什么，以及它和 CSS 多列流、按序取模有什么差别。

## 是什么

**最短列瀑布流（shortest-column masonry）** 是一种列式图墙排版算法：维护 \(k\) 个列的当前底部高度；每来一张不定高卡片，把它堆到当前高度最低的那一列底部；若有多列同高，取列号最小的一列（最左侧）。Pinterest 一类产品页、以及 [Masonry by David DeSandro](https://masonry.desandro.com/) 等脚本库，本质上都按这条贪心规则（或加上测高、缓存、加载后再校正）往下堆。

它解决的是「保留原始宽高比」时的列高失衡：卡片高度随内容变化，不能用固定行高网格硬裁切。算法不重新排序整墙的语义编号，只决定每张卡片进哪一列、落在该列的哪个竖直位置。

## 怎么工作

### 直觉画面

把每一列想成一根从顶往下长的砖柱。新砖到来时，先看哪根柱子目前最短，就把砖砌到那根柱顶；两根一样短时优先砌左边，这样「同一高度带」仍从左往右填，阅读时还能认出从左到右、再往下的节奏。

Round-robin 不管柱子长短，只按编号轮流塞：第 0 张进第 0 列、第 1 张进第 1 列……纵幅一旦集中到某几列，那些列会越来越长，往下滚时一边已经空了、另一边还在拖尾。CSS `columns`／多列布局则是另一条路：内容往往先填满一列再换下一列（或由 `column-fill` 做事后均衡），DOM 源顺序沿列纵向前进，键盘与读屏也常变成「先整列再下一列」，和「行优先扫视」不一致。

### 形式定义（挂回直觉）

记列数为 \(k\)，列宽为 \(w\)（等宽），间距为 \(g\)。第 \(i\) 张卡片的宽高比为 \(a_i\)（宽／高），则缩放后高度

\[
h_i = \frac{w}{a_i}.
\]

维护列高向量 \(H=(H_0,\ldots,H_{k-1})\)，初值全 0。对每张卡片按源顺序做：

\[
c^\star = \arg\min_{c\in\{0,\ldots,k-1\}} (H_c,\, c),
\]

即先比高度，高度相同再比列号（最左）。放置后更新

\[
H_{c^\star} \leftarrow H_{c^\star} + h_i + g.
\]

指标用两套口径核对观感：

1. **`height_spread`**：\(\max H - \min H\)（去掉末尾多余间距后），直接对应「个别列特别长」。
2. **顶边阅读顺序**：按卡片顶边 \(y\) 升序、同 \(y\) 再按 \(x\)、再按编号排序，得到编号序列 \(\sigma\)；相对理想序列 \(1..n\) 统计**逆序对**数，并算 Kendall \(\tau = 1 - 2\cdot\mathrm{inv}/\binom{n}{2}\)。\(\tau\) 越接近 1，顶边扫视越接近编号顺序。

### 可核对的小例子

设定：SEED=**42**，**30** 张纯色矩形，编号 1～30；`aspect = 9/16 + u·(16/9 − 9/16)`，\(u\sim\mathrm{Uniform}(0,1)\)；画布逻辑宽 **1200** px，列间距与卡间距 **10** px，列等宽。脚本打印（与素材目录 `metrics.json` 一致）：

| 算法 | 列数 | height_spread | 逆序对 | Kendall τ |
| --- | ---: | ---: | ---: | ---: |
| Round-robin | 2 | **389.99** | 13 | 0.9402 |
| Round-robin | 3 | **338.82** | 12 | 0.9448 |
| Round-robin | 4 | **732.64** | **38** | **0.8253** |
| Shortest-column | 2 | 390.62 | **0** | **1.0000** |
| Shortest-column | 3 | **111.93** | **0** | **1.0000** |
| Shortest-column | 4 | **136.83** | **0** | **1.0000** |

三列、四列时最短列把列高差压到 round-robin 的约三分之一到五分之一；二列时两者 spread 接近（样本方差下贪心优势变小），但最短列的顶边顺序仍更干净。演示图左侧为三列 round-robin，右侧为三列最短列：右侧两根「砖柱」底部更齐，编号按顶边扫下去也不乱跳。

## 复杂度和代价

- **朴素实现**：每张找最短列 \(O(k)\)，合计 \(O(nk)\)。图墙 \(k\) 多为 2～6，相对测高与图片解码可忽略。
- **堆优化**：列高用优先队列可到 \(O(n\log k)\)；\(k\) 很小时收益不大。
- **懒加载追加**：只对新增项继续贪心，已放置项坐标可保持不变（仅追加场景）。
- **中段插入／删卡／改列数**：通常要从变更点起重排之后，或接受局部重平衡；改列数等于换 \(k\)，对当前集合重跑一遍即可。
- **测高成本**：真实页面还要等图片／异步内容量高；库常见做法是先离屏测高再进最短列（Pinterest Gestalt Masonry 文档即按此描述）。

## 应用场景

- **个人作品图墙**：摄影、渲染、UI 截图混排，要保留原始比例又不愿某一列拖很长。
- **内容流／灵感板**：Pinterest 式瀑布；脚本库或自研绝对定位均可。
- **产线看板缩略图**：缺陷照片、工位快照高度不一，需要多列浏览且大致齐脚。
- **数字孪生照片墙**：仿真截帧与实拍对照卡混排，懒加载追加新帧时不必整墙跳动。
- **响应式改列**：视口变宽加列、变窄减列，对当前集合重跑 \(O(nk)\) 贪心即可。

## 实例一：个人站图墙选型

现状若是 round-robin（`i % cols`），横纵混杂时 3／4 列列高差会明显拉开，按顶边读编号也会在列多时变乱（上表四列逆序对 38）。换成最短列贪心、并列取最左后：同一批 30 张、同一 SEED 下 3 列 spread 从约 339 降到约 112，顶边逆序对降到 0。实现上维护一个长度等于列数的高度数组，每张卡片量高后 `argmin`，再用绝对定位或 `transform` 写坐标。尾部无限滚动只需对新卡继续贪心；响应式改列数则整表重算一次。

不要用 CSS `columns` 冒充同一语义：多列流的阅读顺序与增量「下一张进最短列」都不等同；`column-fill: balance` 是事后均衡连续文本，不是卡片级在线贪心。固定行高网格能保证顺序与齐脚，但会裁切或留白，属于另一种产品形态。

## 实例二：产线看板／数字孪生照片墙

假设看板三列展示当日缺陷图：横幅全景、纵幅特写、近方裁切混在同一流。Round-robin 会让「连续几张纵幅」落在同一取模列上，该列底部远超邻列，操作员往下滚时一侧空白、一侧还在加载。最短列把下一张特写塞进当前最矮列，列脚更齐，顶边扫视仍接近上传顺序（并列偏左保住左→右节奏）。孪生侧把仿真截帧与实拍并排进同一墙时，同样规则适用；异步解码完成后再校正单卡高度并局部重排该卡之后的项，是常见工程补丁，算法骨架不变。

## 短代码（调用核对）

```python
def layout_shortest(aspects, n_cols, col_w, gap):
    """Next card → current shortest column; ties → leftmost."""
    heights = [0.0] * n_cols
    placed = []
    for i, aspect in enumerate(aspects):
        c = min(range(n_cols), key=lambda k: (heights[k], k))
        h = col_w / aspect
        placed.append({"id": i + 1, "col": c, "x": c * (col_w + gap),
                       "y": heights[c], "w": col_w, "h": h})
        heights[c] += h + gap
    heights = [max(0.0, ht - gap) if ht > 0 else 0.0 for ht in heights]
    return placed, heights
```

## 局限和要注意的地方

1. **贪心非全局最优。** 只保证每一步选当前最短列；若允许重排已放置项或预知全部高度，列高差还可能再压，但增量与实现成本上升。
2. **高度必须可信。** 未测高就按占位高度进列，图片解码后真实高度变化会造成重叠或空洞；需测高缓存或加载后再平衡。
3. **中段编辑会牵动后面。** 删除或插入一张后，严格对齐最短列语义通常要重排后续项。
4. **二列优势变小。** 本种子下 2 列时 spread 与 round-robin 接近；列数≥3 时差距更明显。
5. **「近最短窗口偏左」折中未必更好。** 同目录实验里允许小幅 slack 后，列高差反而变大，不能替代纯最短列。

## 延伸思考

1. 固定 SEED=42，把卡片数从 30 扫到 120，画 3 列下两种算法的 `height_spread` 随 \(n\) 的曲线。
2. 给最短列加上「加载完成后按真实高度局部重排该卡之后」的一步，对照只追加不重排时的重叠次数。
3. 用同一批 aspect，实现 CSS multi-column 的「先填满一列」语义（离线模拟），统计顶边序列的逆序对，与最短列对照。
4. 阅读 MDN 多列布局与 CSS Grid Lanes（原生 masonry 方向）文档，标出「在线最短列」与「引擎打包」在增量追加场景下的差异。
