# 心得笔记配图压缩与多台电脑同步需求

- 文档版本：第 3 版（2026-10-13，已吸收桌面工程师的代码体检报告和用户的最终裁决；2026-10-15 补充多篇笔记一起上页时，后面某一篇写盘失败不会撤回前面已经上页的笔记）
- 适用仓库：Dugege007/personalworks-site
- 适用程序：`工具/网站资源编辑工具/`（下文简称「工具」，是用 C# 和 .NET 8 编写的 WPF（Windows Presentation Foundation，微软的 Windows 桌面界面框架）程序）

## 1. 背景

1. 心得笔记既由用户本人写，也会由人工智能写。用户希望在不同的设备和平台上（例如另一台 Windows 电脑、Mac 电脑，或者手机和网页上的编辑器）写笔记或修改笔记，并把笔记同步到其他设备。投放箱里的心得原稿位于 `作品中转站/心得（notes）/{日期_时间}/`，每篇包含 `正文.md`、`心得.json`、配图，以及工具上页时生成的 `.site-ready/` 网页成品文件夹。
2. 2026-10-13 已修改 `作品中转站/.gitignore`，放行心得栏目下的 `.md`、`.json` 和 `.txt` 文字文件，使笔记正文能通过 Git 在多台电脑之间同步。配图目前仍然只留在本机。
3. 为了让另一台电脑拉取仓库后得到完整的笔记，配图也需要进入 Git。配图进入 Git 之前必须先压到合理大小，否则仓库会越来越大、越来越慢。因此需要在工具的心得栏目中加入「超限检测」和「一键压缩」功能，并配套原图备份、恢复和多台电脑同步规则。
4. 现状限制：上页（把笔记和配图压成网页格式并登记到网站内容中）和发布上线（把网站构建后部署到线上），目前只能在安装了网站资源编辑工具的 Windows 电脑上完成，因为工具是只能在 Windows 上运行的 WPF 程序，发布所需的配置文件 `.env.deploy` 也只在这台电脑上。所以本期的工作方式是：**在任意设备上写笔记，通过 GitHub 同步；在装了工具的 Windows 电脑上上页并发布。**

### 1.1 目标

1. 让用户本人和人工智能都能在不同的设备和平台上写笔记，并通过 GitHub 把笔记的正文和配图同步到其他设备。
2. 同步过来的笔记，能在装了工具的 Windows 电脑上直接上页并发布上线网站，不需要再手动补图或整理。
3. 配图在进入 Git 之前就被压到合理大小，保持仓库轻巧。
4. 多台设备同时修改时不丢内容、不静默覆盖。

## 3. 详细需求

### 3.1 阈值

1. 普通配图（JPG、PNG、WebP）单张大小上限默认 500 KB。
2. GIF 单张大小上限默认 2 MB。
3. 两个阈值都可以在「工作区 → 设置…」中调整，修改后立即生效（设置窗口保存后触发一次「重新计算超限状态」）。
4. 阈值保存在仓库里的配置文件 `工具/网站资源编辑工具/profiles/note-image-limits.json` 中，不保存在本机设置里，保证多台电脑判断一致。文件不存在时，使用默认值 500 KB 和 2 MB。修改阈值后要像其他文件一样提交并推送。
5. 单位换算按 1 KB = 1024 字节、1 MB = 1024 KB 计算，与检视栏现有的大小显示规则一致（1024 KB 及以下写整数 KB，再大写 MB，保留两位小数，末尾的 0 不写）。
6. 超限的判定规则是「文件大小严格大于阈值」，等于阈值不算超限。

### 3.2 检测与提示

1. 检视栏选中任意图片时，照常显示文件大小（现有功能，保持不变）。
2. 在心得栏目（下文称「笔记栏」）中选中一张超过阈值的配图时，检视栏的大小数值旁边增加醒目提示：红色或橙色的警告标记，加上一行文字说明超了多少（文案见第 4 节）。
3. 选中一篇笔记，或者笔记内容发生变化（投放箱自动刷新触发）时，底栏显示一条简短提示，例如「本篇有 3 张配图超限」。没有超限配图时不显示这条提示。
4. 笔记栏网格中的超限配图卡片也加一个小角标，方便一眼看出是哪几张。
5. 检测只统计这篇笔记文件夹内的配图，不统计 `.site-ready/` 和 `.originals/` 两个子文件夹里的文件。

### 3.3 一键压缩

1. 检视栏和底栏提供「一键压缩超限配图」按钮，作用范围是当前选中的笔记。也允许在笔记栏多选几张配图后，用右键菜单「压缩所选配图」只压这几张。
2. 压缩一律按原格式输出，文件名和扩展名都不变，这样 `正文.md` 里对配图的引用不需要改。
3. 允许有损压缩，但要尽量保证画质。总策略是「按质量从高到低逐级尝试，一旦压到阈值以下就停止」。
4. JPG 的压缩步骤：
   1. 先做无损优化（去掉冗余数据、优化编码表）。如果已经低于阈值，就停止。
   2. 再按质量 92、88、85、80、75、70 的顺序逐级重新编码，每一级都检查大小，低于阈值就停止。
   3. 如果到质量 70 仍然超限，并且图片长边超过 2560 像素，就把长边等比缩小到 2560 像素，再从质量 92 起重新逐级尝试。
5. PNG 的压缩步骤：
   1. 先做无损优化。如果已经低于阈值，就停止。
   2. 再做有损的减少颜色数量（量化），质量区间从高到低逐级尝试，低于阈值就停止。
   3. 如果仍然超限，并且长边超过 2560 像素，就把长边等比缩小到 2560 像素，再重复上面两步。
6. WebP 的压缩步骤：与 JPG 相同，按质量从高到低逐级尝试，必要时长边缩到 2560 像素。（已与用户确认。）
7. GIF 的压缩步骤：
   1. 先做无损优化（去掉相邻帧里重复的部分，只保留变化区域）。
   2. 再逐级减少颜色数量，例如 256、128、64 色。
   3. 如果仍然超过 2 MB，再逐级降低帧率（隔帧丢弃）或者把尺寸缩小，例如缩到原来的 75%、50%。隔帧丢弃时，把被丢弃帧的显示时长加到保留的相邻帧上，保持总播放时长不变。
   4. 目标是压到 2 MB 以下。
8. 所有尝试都用完以后仍然超限的图片，不再继续压缩，在结果中单独列为「压缩后仍超限」，由用户自己决定怎么处理（比如换图、裁剪或接受现状）。这类图片仍然保留原图备份，压缩后的结果也保留（如果压缩后比原图小），用户可以随时恢复原图。
9. 如果压缩后的文件反而比原图大，就放弃这次结果，保留原图，并在结果中说明。
10. 压缩过程沿用现有的进度窗：显示当前第几张、共几张、当前尝试到的质量级别。结束后弹出结果框，逐张列出：原大小、新大小、最终质量参数、是否缩小尺寸、成功或失败原因。结果同时写入本机 `run.log`。最终质量参数只记录在结果框和 `run.log` 里，不另建缓存文件。
11. 压缩、恢复原图和清理备份都在现有进度窗（`ProgressDialog.Run`）内执行，执行期间设置「正在执行」状态，暂停投放箱监视引起的自动刷新，结束后统一刷新一次。临时文件放在同一文件夹，文件名以 `.` 开头并带固定后缀（例如 `.a.png.compressing`），不被编目识别。

### 3.4 原图备份、恢复原图与重新压缩

1. 原图不放进回收站。压缩前，把原图移动到这篇笔记文件夹下的 `.originals/` 子文件夹，文件名不变。配图在子文件夹里时，保持相同的相对路径，例如 `图/a.png` 备份到 `.originals/图/a.png`。
2. 每张图只保留一份原图备份。如果 `.originals/` 里已经有同名原图（说明这张图已经压过），就不再覆盖备份，始终以最早的原图为准。
3. `.originals/` 不进 Git，只留在本机。
4. 压缩过的图片在检视栏显示「已压缩」标记，并提供两个按钮：
   1. 「恢复原图」：用 `.originals/` 里的原图替换当前图片，然后删除这份备份（恢复后它就是当前文件了，不需要再保留两份）。
   2. 「重新压缩」：总是从 `.originals/` 里的原图重新压缩，不在已经压过的图上反复压，避免画质越压越差。用户可以在弹出的小窗里换一个质量参数（例如选择「更高画质」或手动填质量数值），也可以选择「按默认规则自动」。用户手动选择的质量参数如果让结果超过阈值，允许保存，但在结果中列为「压缩后仍超限」。
5. 提供「清理原图备份」：在「工作区 → 设置…」里提供全局清理，在笔记栏右键菜单里提供「清理本篇原图备份」。执行时把对应 `.originals/` 里的原图送进回收站（这是唯一会把原图送进回收站的操作），执行前弹出确认框，并显示将清理的文件数量和总大小。
6. 只要某张图在 `.originals/` 里有备份，就视为「已压缩」。工具不另外维护压缩记录文件。

### 3.5 EXIF 照片信息

1. 默认保留拍摄参数和拍摄时间（相机型号、光圈、快门、感光度、焦距、拍摄时间等），以及图片方向信息。
2. 默认去掉 GPS（全球定位系统）位置信息，避免泄露隐私。
3. 在设置中提供开关：「压缩时去掉 GPS 位置（默认开）」和「压缩时保留拍摄参数（默认开）」。
4. PNG 和 GIF 通常不带 EXIF，有的话按同样规则处理。
5. 注意：现有上页流程会读取原片的拍摄时间（`MediaCaptureTime.cs`），压缩后的图片必须保留拍摄时间，否则上页后的排序时间会变化。

### 3.6 文件被占用

1. 压缩、恢复原图或清理备份之前，先检查文件能否以独占方式打开。
2. 如果文件被其他程序占用（例如正在 Typora 或看图软件里打开），就跳过这一张，继续处理其余的图片，不让整批中断。
3. 结果框中把被跳过的图片单独列出，提示用户「请关闭占用这张图片的程序后重试」。能识别出占用程序名称时一并显示（可使用 Windows 的重启管理器接口查询，查询不到时只显示通用提示）。
4. 结果框和检视栏提供「重试」按钮，只重新处理被跳过的那些图片。
5. 移动原图和写入新图必须是可回退的：先把压缩结果写到临时文件，确认成功后再移动原图、改名临时文件。任何一步失败都要还原到压缩前的状态，不能出现「原图已移走、新图没写成」的情况。
6. 替换完成后，把原文件的创建时间写回新文件，保证没有 EXIF 拍摄时间的配图（截图、PNG、GIF 等）在网格中的排序不变；修改时间则保持为新的时间，让缩略图缓存能刷新（体检报告第 2.4 条）。

### 3.7 已发布配图禁止压缩

1. 判断以现有代码 `NoteCatalog.ApplyPublishState` 为准，按**单张配图**判断。一张心得配图满足下列任一条件，就视为「已发布」：
   1. 主条件：心得索引 `PersonalSite/src/content/notes/index.json` 中存在一条条目，同时满足「条目的文件夹名 `Folder` 与这篇笔记的文件夹名相同」「`Draft` 为假」「`Slug` 不为空」，并且这张配图的投放箱相对路径出现在该条目的 `Images` 列表里。
   2. 兜底条件：媒体台账 `PersonalSite/src/content/media-ledger.json` 中这张配图的状态是 `published`（台账记录的 `stageRel` 或 `sourceStageRel` 指向这张原图）。这用来挡住上页中途失败、台账已写而索引没写的情况。
2. 只要配图发布过，不管这篇笔记现在是显示还是已隐藏，一律不能压缩、恢复原图或重新压缩。原因是隐藏不会撤掉线上的对象，恢复显示时也不会重新上传，本地替换后会和线上版本对不上。
3. 不属于「已发布」的情况（允许压缩）：`Draft` 为真或 `Slug` 为空的条目下的配图；文件夹已登记、但这张配图不在 `Images` 列表里（例如上页后新加的配图），并且台账里也没有 `published` 记录。
4. 对已发布的配图，压缩相关按钮置灰，鼠标悬停时显示「这张配图已发布到网站，不能压缩」，不给操作建议。
5. 一键压缩时自动跳过已发布的配图，并在结果中列出「已发布，已跳过」。
6. 判断写成核心层的一个纯函数（建议 `NoteImageGuard`），检视栏按钮、一键压缩和右键菜单都调用它，不各写一遍。

### 3.8 配图进入 Git

1. 修改 `作品中转站/.gitignore`，在现有规则基础上放行心得栏目的配图（压缩后的成品），建议规则如下（实现时须用 `git check-ignore -v` 逐条验证）：

   ```gitignore
   # 心得栏目的配图（压缩后的成品）也进 Git
   # 只放行笔记文件夹里的配图（至少一层子文件夹），大写和小写扩展名都放行
   !*notes*/*/**/*.[jJ][pP][gG]
   !*notes*/*/**/*.[jJ][pP][eE][gG]
   !*notes*/*/**/*.[pP][nN][gG]
   !*notes*/*/**/*.[wW][eE][bB][pP]
   !*notes*/*/**/*.[gG][iI][fF]
   # 网页成品和原图备份不进 Git
   *notes*/**/.site-ready/**
   *notes*/**/.originals/**
   ```

   排除规则必须写在放行规则之后，Git 按最后一条匹配的规则生效。大写写法是因为 Git 在 Linux 和 macOS 上默认区分大小写，手机或其他设备上可能出现 `.JPG` 这样的扩展名。心得栏目根目录下（不在任何笔记文件夹里）的配图不进 Git。
2. 摄影、视频等其他栏目继续不进 Git，规则不变。
3. 缺失配图标记：另一台电脑拉取仓库后，如果 `正文.md` 里引用的配图在本机不存在，工具要在笔记栏和检视栏标出「缺失配图」，列出缺失的文件名；底栏提示例如「本篇有 2 张配图缺失」。缺失配图的笔记禁止上页。检测要一次列出全部缺失项，不能遇到第一张缺失就停止。

### 3.9 多台电脑同步规则（所有项目通用）

本规则适用于用户的所有项目和所有 bot，不只适用于这个工具。

1. 开工前必须同步：无论是用户本人还是人工智能，修改任何内容之前先拉取最新版本（`git pull --ff-only`）。拉取失败或出现冲突时，停下来报告，不做任何修改。
2. 工具内检查：工具在后台执行 `git fetch` 并比较本地分支与 GitHub 上对应分支，同一工作区 60 秒内最多执行一次，选中笔记时使用最近一次的结果，不卡界面。如果本地落后于 GitHub，就显示提示「本地版本落后于 GitHub，请先同步」，并禁止工具内所有会写投放箱或心得索引的操作（压缩、恢复原图、清理备份、星级和标签草稿、上页、隐藏、恢复显示），直到同步完成。工具无法阻止 Typora 保存，用 Typora 打开时只给提示。网络不通、无法检查时，给出提示「无法连接 GitHub，同步状态未知」，由用户决定是否继续。
3. 小步提交、尽快推送：改完一篇笔记就提交并推送，不在本地攒一大堆改动。
4. 冲突不自动合并：一旦出现冲突，不使用任何自动合并策略，把两边的版本（本地版本和 GitHub 版本）都摆出来，让用户裁决保留哪一个或怎样合并。
5. 这套规则在本文档确认后，由 Grok Bot 发给所有 bot。

### 3.10 多篇笔记一起上页

1. 一次标记多篇笔记上页时，先检查每一篇是否标记了正文、是否有缺失配图、是否有引用超出笔记文件夹。只要有一篇不通过，就一篇都不上页，提示里写出每一篇的笔记标题和原因。
2. 全部检查通过之后，按选中顺序逐篇写盘。如果后面某一篇因为写盘出错而失败，前面已经上页的笔记不会自动撤回。失败提示要写明哪几篇已经上页、哪一篇失败，以及失败原因。例如第一篇「清晨散步」已经上页、第二篇「控制图」写盘失败时，提示为两句：「清晨散步」已经上页，不会自动撤回。「控制图」上页失败：压图失败：……。用户需要自己处理已经上页的那几篇。
3. 第一篇就失败时，没有已经上页的笔记，提示只说明失败的这一篇和原因，不写「已经上页」或「撤回」。
4. 这与第 2.2 节第 10 条不是同一件事。第 10 条说的是单篇内部上页中途失败，媒体台账已经写成已发布，心得索引还没有写，本期不做回滚。本条说的是多篇笔记之间：已经完整上页的那几篇也不撤回。
5. 上页预演的拒绝行除了文件名，还要写上这篇笔记的标题。批量检查弹窗已经使用笔记标题；多篇笔记一起预演时，如果拒绝行只有文件名，同名配图分不清是哪一篇。标题优先用项目栏里的笔记标题，项目栏没有时用正文一级标题。

## 5. 验收标准

每一条都应能由人或自动测试验证。

1. 把普通配图阈值设为 500 KB：一张 501 KB 的 JPG 被标为超限，一张恰好 500 KB 的不被标出。
2. 在设置中把阈值改成 300 KB 后，不重启工具，超限标记立即更新；仓库里的配置文件随之改变，另一台电脑拉取后得到相同阈值。
3. 一篇有 3 张超限配图的笔记，选中后底栏显示「本篇有 3 张配图超限」；全部压缩成功后，这条提示消失。
4. 一键压缩后：文件名、扩展名不变，`正文.md` 不需修改；成功的图片都不超过阈值；`.originals/` 里有同名原图，内容与压缩前完全一致（哈希值相同）。
5. 质量逐级尝试：用一张在质量 85 时刚好低于阈值的 JPG 测试，结果记录的最终质量为 85，而不是更低。
6. 一张 6000×4000 像素、质量 70 仍超限的 JPG，压缩后长边为 2560 像素，比例不变。
7. 一张无论如何都压不到阈值以下的图片，被列为「压缩后仍超限」，原图备份存在。
8. 一张 5 MB 的 GIF 压缩后不超过 2 MB，并且仍然是能正常播放的动图。
9. 「重新压缩」两次后，结果与直接从原图压缩一次的结果一致（证明每次都从原图出发）。
10. 「恢复原图」后，当前文件与原图哈希值相同，`.originals/` 中这张的备份被删除。
11. 「清理本篇原图备份」后，原图出现在 Windows 回收站中，`.originals/` 为空或被删除。
12. 带 GPS 的 JPG 压缩后：GPS 信息不存在，相机型号、拍摄时间和方向信息仍存在。
13. 在看图软件中独占打开一张图后执行一键压缩：这张被跳过并给出提示，其余图片正常完成；关闭看图软件后点「重试」，这张压缩成功。
14. 在写入新图的过程中模拟失败（例如磁盘写入异常）：原图仍在原位置，没有丢失。
15. 已发布配图（分别测试：主条件满足且显示中；主条件满足但整篇已隐藏；只有媒体台账为 `published`）：压缩按钮置灰，悬停文案为「这张配图已发布到网站，不能压缩」；一键压缩时被列为「已发布，已跳过」。`Draft` 为真、`Slug` 为空、或不在 `Images` 列表且台账无记录的配图允许压缩。
16. 修改 `.gitignore` 后，在 `core.ignorecase=false` 下用 `git check-ignore -v -n --no-index` 验证：笔记文件夹里的配图（包括 `.JPG` 等大写扩展名、子文件夹里的配图、GIF）不被忽略；心得栏目根目录下的配图被忽略；`.originals/` 和 `.site-ready/` 下的文件被忽略；摄影、景观效果图等其他栏目的文件仍被忽略。这组断言写成自动测试。
17. 在另一个克隆里删除一张配图：工具标出「缺失配图」，底栏显示缺失数量，这篇笔记禁止上页。
18. 让本地落后 GitHub 一个提交：打开笔记时出现落后提示，保存和压缩按钮不可用；同步后恢复可用。
19. 断网时打开笔记：出现「同步状态未知」提示，工具不崩溃。
20. 含 GIF 配图的笔记执行上页预演时，预演明确拒绝并提示「GIF 配图暂不支持上页」，工具不崩溃。
21. 前置修复（第 10 节）各条都有对应的自动测试：心得索引内容损坏或含 Git 冲突标记时报错并禁止写入，不会被覆盖成空表；`.originals/` 里的文件不出现在网格、不参与超限统计、不会被上页；本机设置写到一半失败时原文件完好。
22. 一张没有 EXIF 拍摄时间的 PNG 压缩后，文件创建时间与压缩前相同，网格排序位置不变；修改时间变新，缩略图刷新。
23. GIF 降帧后总播放时长与压缩前相同（允许 1 帧时长以内的误差）。
24. 压缩一批配图的过程中，投放箱网格不反复重载，结束后只刷新一次。
25. 现有测试（`dotnet test`）全部通过，并为压缩规则、阈值判定、备份与恢复、`.gitignore` 规则补充新的测试。

## 6. 技术选型

要求：只使用免费的开源组件，优先复用现成的库或命令行工具。

| 组件 | 用途 | 许可证 | 结论 |
| --- | --- | --- | --- |
| Magick.NET（ImageMagick 的 .NET 封装） | JPG、PNG、WebP、GIF 的读写、缩放、质量重编码、EXIF 读写（可以单独删除 GPS 字段） | Apache License 2.0；底层 ImageMagick 使用 ImageMagick License（Apache 2.0 风格的开源许可证） | **已选定为主库**（建议使用 `Magick.NET-Q8-AnyCPU` 包，Q8 指每个颜色通道 8 位，对网页配图足够）。一个 NuGet 包覆盖全部格式和 EXIF 处理，免费开源，可以放在核心层用 `dotnet test` 自动测试 |
| pngquant | PNG 有损减色（质量区间参数正好对应「从高到低逐级尝试」） | GPL v3（GNU 通用公共许可证第 3 版）或商业许可证 | **推荐**，以独立命令行程序调用（像现在调用 FFmpeg 一样），不链接进工具代码，不影响工具本身的许可证 |

| SixLabors.ImageSharp | 图像处理 | Six Labors Split License 1.0 | **不推荐**。只有在「用于开源或源码公开的软件」「作为间接依赖」「年营收低于 100 万美元的个人或公司」「非营利组织」这几种情况下才按 Apache 2.0 授权，其余情况需购买商业许可。用户个人使用目前满足条件，但它不是标准的开源许可证，条件变化时会有风险，不满足「免费开源」的要求 |

实现建议：

1. 主流程用 Magick.NET 完成格式识别、缩放、质量重编码和 EXIF 处理。PNG 和 GIF 的专门优化交给 oxipng、pngquant 和 gifsicle 命令行程序，参照现有 FFmpeg 的调用方式：在设置中可以指定程序路径，找不到程序时，对应步骤跳过或给出明确提示（例如「没有找到 pngquant，PNG 只做无损优化」），不让工具崩溃。
2. 新建统一的外部程序查找入口（建议 `src/SiteMediaStudio.Core/IO/ExternalToolLocator.cs`），按「设置里填写的路径 → 常见安装位置 → 系统 PATH 环境变量」三级查找并探测版本，三个新程序都用它，不再照抄现有 FFmpeg 的查找代码。
3. 命令行程序的 Windows 版本可以从各自官方网站或 Scoop、winget 等包管理器安装，安装方法写进工具的 README。
4. 本期不使用 Python 的 Pillow 库实现新功能。现有上页时压 WebP 的脚本 `prepare-initial-batch.py` 仍使用 Pillow，本期不迁移。
5. 压缩逻辑放在 `SiteMediaStudio.Core`（建议新建 `src/SiteMediaStudio.Core/Notes/NoteImageCompressor.cs` 等文件），界面部分放在 `SiteMediaStudio` 窗口项目，便于命令行版本以后复用。

## 7. 风险

1. 未压缩的大图误进 Git 历史后难以清除（进入历史后即使删除也会一直占用仓库体积）。本期不做提交前检查，对策是：工具的超限提示，以及「开工前同步、提交前先压缩」的使用习惯；以后视情况再加提交前检查。
2. `.originals/` 只有一份本机备份，硬盘损坏会丢失。用户已接受，重要原图依靠平时的整机备份。
3. 多台电脑同时修改同一篇笔记会冲突。对策：第 3.9 节的同步规则和工具内检查。
4. 有损压缩可能让截图里的文字边缘变模糊。对策：逐级尝试、优先高质量，并提供恢复原图和重新压缩。
5. GIF 压到 2 MB 可能明显掉帧或变糊。对策：仍超限时交给用户决定；转 MP4 以后再做。
6. 外部命令行程序缺失或版本不同，压缩结果可能不一致。对策：设置中显示检测到的程序版本，缺失时降级处理。
7. 压缩时去掉或改写 EXIF 可能影响现有按拍摄时间排序的功能。对策：第 3.5 节第 5 条，必须保留拍摄时间并加测试；没有 EXIF 拍摄时间的配图按第 3.6 节第 6 条保留创建时间。
8. 工具 README 第 74 行「心得索引只收录、没有这条台账的正文和配图」与代码不符：心得配图上页时实际会写入媒体台账（只有正文 `正文.md` 和台账记录缺失的异常配图才没有台账）。容易误导后来的实现者，由桌面工程师在本期顺手修正 README。
9. 心得索引参与多台电脑同步后，Git 冲突标记可能让索引解析失败。对策：第 10 节前置修复第 1 条。

## 10. 前置修复（开工前必须先改）

以下五条来自桌面工程师的代码体检报告。不先修改，本期功能会出错或丢数据。每条作为独立提交，在新功能之前完成，并补充测试。

1. **心得索引读取失败时不再静默返回空表。** 现状：`src/SiteMediaStudio.Core/Notes/NoteIndexStore.cs` 的 `LoadFile` 遇到 JSON（一种文本数据格式）解析错误时返回空索引，随后上页、隐藏、恢复显示会把空索引整份写回，抹掉全部心得。本期起 `index.json` 参与多台电脑同步，Git 冲突标记会触发这个问题。改法：解析失败时报错（带文件路径），界面显示「心得索引损坏或有冲突，请先修复」，并禁止所有写入索引和压缩配图的操作；文件不存在时仍按空索引处理。
2. **统一排除 `.originals/`。** 现状：排除 `.site-ready/` 的逻辑写了三遍（`src/SiteMediaStudio.Core/Catalog/MediaPathRules.cs` 的 `IsDerivedStageRel`，`src/SiteMediaStudio.Core/Notes/NoteRules.cs` 的 `FindBlockedFile` 和 `ListLocalImages`），都没有 `.originals/`。不改的话，原图备份会出现在网格里、参与超限统计，甚至被上页公开到线上。改法：在 `MediaPathRules` 中提供一个统一判断，同时识别 `.site-ready` 和 `.originals`，`NoteRules` 两处改为调用它；`.originals` 定义为常量。
3. **本机设置保存改为原子写入。** 现状：`src/SiteMediaStudio.Core/Profile/AppSettingsStore.cs` 的 `Save` 直接整份写文件，写到一半中断会产生损坏文件，下一次读取时静默变回默认值，再保存就覆盖掉用户的全部设置。改法：先写临时文件，再替换原文件。（照片信息开关和外部程序路径仍是本机设置，所以这条本期必须改。）另外，设置窗口保存后要触发「重新计算超限状态」。
4. **设置窗口改为可滚动并分组。** 现状：`src/SiteMediaStudio/Views/SettingsWindow.cs` 固定 520×520 像素、不可调整大小、没有滚动条，放不下本期新增的设置项。改法：内容区包进可滚动容器，按「缩略图缓存」「心得配图」「外部程序」分组。
5. **拆分心得配图的扩展名集合。** 现状：`MediaPathRules.ImageExtSet` 包含 `.gif`，`NoteRules.ImageExtSet` 只有四种，`NoteRules.BlockedExtSet` 又把 `.gif` 列为禁止，三份口径不同。改法：在 `NoteRules` 中拆分为「心得允许存放的配图」（加入 `.gif`）和「心得允许上页的配图」（仍是 `.jpg`、`.jpeg`、`.png`、`.webp` 四种）；上页预演发现文件夹内或正文中有 GIF 时，返回「GIF 配图暂不支持上页」。`.bmp` 本期不处理。

体检报告里另有两条要在新代码的设计中处理（不改旧代码）：压缩替换文件后保留创建时间（已写入第 3.6 节第 6 条），压缩期间暂停投放箱监视的刷新（已写入第 3.3 节第 11 条）。缺失配图检测新建只读的检查逻辑，把正文引用图片的正则表达式（一种文本匹配规则）抽成共用常量（第 3.8 节第 3 条）。

## 附录 A：GitHub Git LFS 免费额度（2026-10-13 核实）

- 出处：GitHub 官方文档「Git Large File Storage billing」，https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-storage-and-bandwidth-usage
- 计算方式：**按账号计算，不按仓库计算**。官方原文为「Each GitHub account includes a quota of free bandwidth and storage」，并说明存储和下载流量始终计入仓库所有者的账号，账号下所有仓库共用这份额度。
- GitHub Free（免费个人账号）和 GitHub Pro：存储 10 GiB，下载流量每月 10 GiB。
- GitHub Team 和 GitHub Enterprise Cloud：各 250 GiB。
- 计费方式已从原来的预付「数据包」改为按实际用量计费。存储按小时累计，每个账单周期清零重新计算；流量额度每个账单周期重置。
- 超出额度：没有绑定付款方式或预算设为 0 美元时不会扣费，但当月会被限制（存储超额后无法推送新的大文件，流量超额后当月停用 Git LFS）。
- 说明：旧的预付数据包时代的额度已经过时，以上述官方文档为准。按本文档的阈值估算（单张 500 KB），心得配图在很长时间内都不需要 Git LFS。
