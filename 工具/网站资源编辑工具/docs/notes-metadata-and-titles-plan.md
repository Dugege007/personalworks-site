# 心得元数据与主副标题：设计与落地计划

文档受众：站点主人 Hongbo Du，以及参与实现的工程机器人（桌面工程师负责资源编辑工具的 Windows Presentation Foundation 客户端改动；前端工程师负责 PersonalSite 展示；秘书负责阶段协调与助手接入）。语气要求完整中文陈述句，长期稳定可扩展。本文确认后即按阶段开工，不另等一轮口头批准；后续调整由用户另行提出。

仓库：`Dugege007/personalworks-site`。生产发布仅走安装包（MSI）；自动化验收优先在 YuePC 上跑。

## 1. 背景与目标

心得栏目已经打通「中转站夹 → 资源编辑工具上页 → PersonalSite 列表与详情」的主路径。当前标题主要来自正文第一个一级标题或 `心得.json` 里的 `title`；发布时间只有索引里的单个 `date`（取自创建日）；`modifiedAt` 虽是字符串数组，但只有时间戳、没有变更说明，详情页也不展示。

用户已确认三条产品方向：

1. **主标题与副标题**从中转站夹名解析，夹名形态为 `主标题——副标题`（间隔使用 Unicode 字符 U+2014 的中文破折号 `——`），不再靠重命名 `正文.md` 来定标题。站点上发布的文件名继续使用 ASCII 形式的 slug，例如 `n-yyyyMMdd-HHmmss.md`。
2. **创建与修订历史**要在详情页可见：顶部一行同时给出创建时间与最近一次修改时间；点击最近修改时间可展开完整修订列表；每条修订含时间戳与简短变更说明（类似一次提交说明）。
3. **修订摘要**在保存或显著编辑时由助手根据内容差异自动生成并写入元数据；用户之后可在资源编辑工具中手工改摘要文案。

本计划把上述方向落成可实现的数据模型、校验规则、管线改动与分阶段验收标准，并标明非目标与后续可调项。

## 2. 术语

| 术语 | 含义 |
|------|------|
| **资源编辑工具** | 仓库内 `工具/网站资源编辑工具` 下的 Windows Presentation Foundation 桌面应用；也常称「资源工具」「编辑工具」「网站资源编辑工具」。负责中转站编辑、上页预演、发布写入与索引维护。 |
| **中转站** | 仓库内 `作品中转站/` 投放区。心得频道路径为 `作品中转站/心得（notes）/{夹名}/`，夹内固定有 `正文.md` 与 `心得.json`。 |
| **slug** | 心得在站点与对象存储路径中的 ASCII 标识，须匹配正则 `^[a-z0-9]+(?:-[a-z0-9]+)*$`。默认形如 `n-yyyyMMdd-HHmmss`。不是中文夹名，也不作为对象存储键的中文片段来源。 |
| **主标题** | 从夹名按第一条 `——` 分割后的左侧文本（去掉首尾空白）。用于站点展示的主名称。 |
| **副标题** | 夹名中第一条 `——` 右侧文本（去掉首尾空白）。可为空；为空时站点只展示主标题。 |
| **修订记录** | 附在元数据里的有序变更条目列表。每条至少含发生时间、短说明，以及生成来源标记。网页展示以元数据为准，不以未筛选的 Git 历史为准。 |

## 3. 现状与缺口

### 3.1 中转站与资源编辑工具

- 新建心得时，`NoteRules.AllocateFolderName` / `CreateFolder` 仍分配形如 `yyyyMMdd_HHmmss` 的夹名；标题同步逻辑 `NoteConfigStore.SyncTitle` 仍从正文第一个 `# ` 一级标题回写 `心得.json` 的 `title`。
- `NoteConfig`（对应 `心得.json`）现有字段：`createdAt`、`modifiedAt`（`string[]`，仅时间戳）、`title`、`slug`、`summary`。没有主副标题分字段，也没有带说明的修订条目。
- `AppendModified` 在发布上线后若正文或配图变新，只追加时间戳字符串，不写变更说明。
- 上页预演 `NoteRules.Plan` 要求正文有一级标题才能通过；标题写入发布计划与索引的 `title`；`date` 取自 `createdAt` 的日期部分。

### 3.2 PersonalSite

- 内容目录：`PersonalSite/src/content/notes/{slug}.md` 与 `index.json`。
- `NoteRecord` / 索引条目目前只有单个 `date`（创建日）、`title`、`summary` 等；前端 `NoteDetailPage` 的页眉踢脚区只显示一个日期；`NotesPage` 列表卡片同样只显示一个日期。
- 标题展示完全依赖索引中的 `title`（历史上来自一级标题或配置），没有副标题字段，也没有修订列表数据结构。

### 3.3 缺口对照

| 缺口 | 说明 |
|------|------|
| 标题来源错误位 | 应用夹名解析主副标题，而不是依赖重命名正文或正文一级标题作为唯一真相。 |
| 修订语义不足 | `modifiedAt` 只有时间，无法支撑「时间 + 短说明」的详情页列表，也无法支持手工改摘要。 |
| 展示不足 | 详情页未同时展示创建与最近修改；列表页策略需明确默认是否仍只显示创建日。 |
| 长度约束缺失 | 夹名一旦承载中文主副标题，资源编辑工具需在约 60 字警告、约 80 字禁止保存，避免过长夹名与过长展示标题。 |
| 管线未对齐 | `NoteRules`、索引写入、前端 `NoteRecord` 均需扩展字段并保持旧稿可读。 |

## 4. 目标数据模型

原则：中转站 `心得.json` 是编辑期权威；上页时把访客需要的字段投影进 `index.json`（以及前端 `NoteRecord`）。正文 `正文.md` 可以保留一级标题作为正文内装饰，但**站点展示用主副标题以夹名解析结果为准**，不再把「是否重命名正文文件」当作标题来源。

### 4.1 `心得.json`（`NoteConfig`）扩展

建议字段（名称可用驼峰，与现有 JSON 风格一致）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `createdAt` | `string` | 创建时间，格式保持 `yyyy-MM-dd HH:mm:ss`（与现有 `NoteConfigStore.TimeFormat` 一致）。 |
| `revisions` | `RevisionEntry[]` | 修订列表，时间新的可放末尾或按约定排序；替代原先仅含时间戳的 `modifiedAt` 作为权威结构。 |
| `title` | `string` | **展示用完整标题**（有副标题时建议存 `主标题——副标题`，或与 `mainTitle`/`subtitle` 同步生成）。保留该字段便于旧代码与列表摘要兼容。 |
| `mainTitle` | `string` | 主标题。 |
| `subtitle` | `string` | 副标题；无副标题时为空字符串。 |
| `slug` | `string` | ASCII slug，不变规则。 |
| `summary` | `string` | 列表用短摘要（与修订条目的 `summary` 不同：前者是文章导语，后者是单次变更说明）。 |

**修订条目 `RevisionEntry` 建议形状：**

```json
{
  "at": "2026-10-05 04:10:11",
  "summary": "补充传感器阈值段落并修正配图引用。",
  "source": "assistant"
}
```

| 子字段 | 说明 |
|--------|------|
| `at` | 该次修订时间，格式同 `createdAt`。 |
| `summary` | 短说明；可由助手自动写入，也可由用户在资源编辑工具中改写。 |
| `source` | 建议枚举字符串：`assistant`（助手根据差异生成）、`user`（用户手改或手填）、`system`（工具在上页/同步等流程中写入的占位或迁移条目）。 |

**向后兼容：**

- 若旧稿只有 `modifiedAt: string[]` 而没有 `revisions`：读取时把每个时间戳迁移为 `{ at, summary: "", source: "system" }`，写回时可一次落盘为 `revisions`（是否立刻删除 `modifiedAt` 由桌面工程师在实现时二选一：短期双写读取、新写只写 `revisions` 更稳妥）。
- 若旧稿只有 `title`、夹名仍是时间戳形态：解析不到 `——` 时，`mainTitle` 可回退为现有 `title` 或正文一级标题；`subtitle` 为空。上页与展示不得因缺副标题而失败。
- 缺少 `mainTitle`/`subtitle` 的旧索引条目：前端用 `title` 整串作为主标题显示。

### 4.2 `index.json` / `NoteRecord` 扩展

在现有 `folder`、`slug`、`title`、`date`、`summary`、`draft`、`hidden`、`previewObjects`、`body`、`images` 基础上增加：

| 字段 | 说明 |
|------|------|
| `mainTitle` | 主标题。 |
| `subtitle` | 副标题，可空。 |
| `createdAt` | 完整创建时间（可选但推荐；若暂不投影，前端可用 `date` + 约定）。 |
| `revisedAt` | 最近一次修订的 `at`；无修订时可空或等于创建时间（实现时统一一种约定并写进测试）。 |
| `revisions` | 与中转站同形的修订数组（上页时整表或按需拷贝）。访客详情页展开列表读此字段。 |

`date` **继续保留**为创建日的 `YYYY-MM-DD`，供列表排序与旧卡片兼容；不要用最近修改日覆盖 `date`，以免列表排序语义漂移。

前端 `NoteRecord`（`select.ts`）与 `NoteCard` 同步扩展上述展示所需字段；缺字段时按兼容规则降级。

### 4.3 版本号

`NoteIndexFile.Version` 当前为 `1`。若字段变更需要读者区分，可在实现 P0/P1 时把索引 `version` 升到 `2`，并在读取端容忍 `version` 缺省或为 `1` 的旧文件。不必为每一次小字段追加都强制升版本，但升一次有助于脚本与测试断言。

## 5. 夹名规则与长度校验

### 5.1 解析规则

1. 夹名字符串按**第一次出现**的 `——`（U+2014 连续两个字符构成的破折号写法，即用户文档中的 `主标题——副标题` 形态）分割。
2. 左侧去掉首尾空白后为主标题；右侧去掉首尾空白后为副标题。
3. 若夹名中**没有** `——`：整段去掉首尾空白后视为主标题，副标题为空。此时允许保存与上页（仍受长度限制）。
4. 若 `——` 左侧为空（例如夹名以 `——` 开头）：视为非法，资源编辑工具应阻止保存或重命名，并提示「主标题不能为空」。
5. 夹名中若出现多个 `——`：仅第一次分割生效，右侧整体（可含更多 `——`）算作副标题文本，避免歧义规则扩散。
6. **不要**用半角 `--`、全角其他破折号变体作为正式分割符；校验与提示文案应明确要求使用 `——`。若实现阶段发现用户常误输入其他字符，可在「待用户后续可调项」中再决定是否做温和纠正，本计划默认不自动替换。

### 5.2 与 slug、正文文件名的关系

- 重命名夹名只影响主副标题与中转站路径；**不**自动把 slug 改成中文，也**不**要求把 `正文.md` 改名。
- 站点发布文件名保持 `n-yyyyMMdd-HHmmss.md` 这类 ASCII slug 文件名。
- 对象存储键继续基于 slug 与相对路径（例如 `notes/{slug}/...`），**禁止**把中文夹名直接当作对象键。

### 5.3 长度：约 60 警告、约 80 禁止

- **计数对象**：用于标题的夹名整段字符数（含 `——` 本身），按 Unicode 标量／.NET 字符串 `Length` 或前端等价的码元约定实现，并在测试中固定样例（含中英文混合）。
- **约 60 字**：达到或超过时给出**警告**，仍允许保存；提示应说明「夹名偏长，列表与详情标题可能折行过多，建议缩短」。
- **约 80 字**：达到或超过时**禁止保存／禁止完成重命名**；提示应说明「夹名过长，请将主副标题总长度控制在 80 字以内（含破折号）」。
- 「约」表示实现时用明确整数阈值即可（建议直接采用 60 与 80），并在单元测试中锁死，避免魔法数散落。

### 5.4 提示文案要点

- 说明正确形态示例：`主标题——副标题`。
- 说明无副标题时可只写主标题。
- 说明主标题不能为空。
- 分别给出警告阈值与禁止阈值的原因（展示与文件系统可读性），不要只弹「太长了」。
- 长度提示与 slug 非法提示分开，避免用户误以为中文夹名要改成英文 slug。

### 5.5 新建夹与后续改名

- 新建时可继续先落时间戳夹名，再由用户改名为带主副标题的夹名；或在创建对话框直接收集主副标题再生成夹名。两种交互任选其一，但**解析与校验必须走同一套 `NoteRules`（或并列的纯函数）**，供桌面界面与测试共用。
- 改名成功后应立即根据新夹名刷新 `mainTitle`、`subtitle`、`title`，并可选追加一条 `source: "user"` 的修订说明（例如「更新标题」），是否自动追加列为 P0 实现细节，默认建议：仅标题变更且正文未变时写一条简短用户源修订，避免空转。

## 6. 修订摘要自动生成与可编辑流程

### 6.1 何时生成

在以下时机由助手（或桌面工具触发的助手调用）根据**内容差异**生成短说明，并写入对应修订条目的 `summary`：

- 用户在资源编辑工具中保存正文（或等价的「显著编辑」提交）且相对上一版有实质差异；
- 上页／发布导致正文或配图集合相对上次已发布状态有实质变化，且需要留下访客可见的修订说明。

「显著」的判定建议：正文文本规范化后的差异非空，或配图集合增删改；纯空白、换行符归一、或仅元数据字段微调是否算显著，由实现定阈值并写入测试。若差异为空，不追加新修订。

### 6.2 存哪里

- 权威存储：该心得夹内 `心得.json` 的 `revisions`。
- 上页时投影到 `PersonalSite/src/content/notes/index.json` 对应条目的 `revisions`（及 `revisedAt`）。
- 不要把修订摘要只写在 Git commit message 里当作网页唯一来源。

### 6.3 如何手改

- 资源编辑工具提供修订列表编辑界面（至少能改每条 `summary` 文本；是否允许删除条目、调整顺序列为可调项，默认允许改文案、不允许随便删历史时间戳以免详情页空洞）。
- 用户保存手改后，将该条 `source` 标为 `user`（或保留原 `at`，另设 `editedByUser: true`——若不想加字段，则用 `source: "user"` 覆盖即可）。
- 手改后的文案随下一次上页进入 `index.json`。

### 6.4 与 Git 的关系

- Git 提交信息**可以**带上与修订摘要相同或相近的文案，便于仓库审计。
- 网页展示与 PersonalSite 数据**只读** `心得.json`／`index.json` 中的 `revisions`。
- **非目标**：把整段 Git 历史无筛选地刷到网页；不在浏览器里直接调用 Git。

### 6.5 助手接入边界

- P0 可先支持：工具在保存时写入带空摘要或占位摘要的修订条目（时间准确），摘要稍后再补。
- P2 再把「根据 diff 自动生成中文短说明」接到秘书／助手流程；生成失败时保留空摘要或固定回退句（例如「内容已更新」），不得阻断保存。

## 7. 网站展示

### 7.1 详情页（必做）

- 标题区：主标题作为主 Heading；若有副标题，以次级样式显示在主标题附近（具体视觉由前端工程师定，但语义上二者分离）。
- 时间行（详情页顶部一行）：同时展示**创建时间**与**最近修改时间**。文案示例方向：「创建于 ……｜最近修改于 ……」（具体标点与是否显示到秒由实现与站点文风统一）。
- **最近修改时间**可点击（或键盘可达的等效控件）：点击后展开／收起完整修订列表。
- 修订列表每行：时间戳 + 短说明；无说明时显示温和占位（例如「（无说明）」），不要留下空白行让人以为坏掉。
- 若尚无任何修订：最近修改可显示为与创建相同，或隐藏「最近修改」而只保留创建——实现时选一种并在验收用例中固定；推荐「无修订时最近修改与创建相同且列表为空或仅提示尚无修订」。

### 7.2 列表页（建议默认）

- **默认建议：列表卡片仍只显示创建日**（继续用现有 `date` → `displayNoteDate`），避免卡片信息过载，也避免「刚改过的旧文」因修改日新而打乱读者对写作时间的直觉。
- 排序继续按 `date`（创建日）新到旧，与现在 `visibleNotes` 一致。
- 若日后要在卡片上增加「近改」小字，列为可调项，不阻塞 P1。

### 7.3 旧稿展示

- 仅有 `title` 时：整串作主标题，无副标题。
- 仅有 `modifiedAt` 时间戳、无摘要：展开列表可显示时间 + 空说明占位。
- 索引缺 `revisions`：不报错，详情页降级为只显示创建日（或创建 + 无展开）。

## 8. 上页／发布管线改动

### 8.1 `NoteRules` 与配置存储

- 新增（或并列）纯函数：`ParseFolderTitles(folderName) → (mainTitle, subtitle, displayTitle)`；长度校验函数返回「通过／警告／禁止」三级结果。
- `SyncTitle` 行为调整：优先从夹名解析写入 `mainTitle`／`subtitle`／`title`；正文一级标题不再覆盖夹名已给出的主副标题。正文无一级标题时，只要夹名能解析出非空主标题，上页预演应可通过（需改掉当前「正文还没有一级标题」的硬失败，或改为仅在主标题与正文标题都空时失败）。
- `Plan`：把 `mainTitle`、`subtitle`、完整 `title`、`createdAt`、`revisions`、`revisedAt` 带进 `NotePublishPlan`。
- `AppendModified`：改为追加 `RevisionEntry`（可先空摘要），而不是只 `string` 时间戳。

### 8.2 索引写入

- `NotePublisher`／`NoteIndexStore` 写入 `NoteEntry` 时投影新字段。
- 保持 `date` = 创建日；`slug` 规则不变；草稿与隐藏逻辑不变。

### 8.3 Frontmatter 策略

- 现行方向已是「正文不放标题和日期」；上页后的站点 Markdown 也以去掉重复一级标题为主。
- 本计划**不要求**把主副标题或修订列表再写回正文 frontmatter。若发布稿仍带旧 frontmatter，继续用现有剥离逻辑即可。
- 若未来要在纯 Markdown 备份里冗余一份元数据，另开任务，不纳入本阶段必做。

### 8.4 测试与发布通道

- 桌面侧：扩展 `NoteRulesTests`、`NoteIndexStoreTests` 等，覆盖解析、长度、旧 `modifiedAt` 迁移、上页字段投影。
- 前端侧：扩展 `notes-select` 等测试，覆盖可见性、日期显示、缺字段降级。
- 自动化优先在 YuePC 验证；生产仍只通过 MSI 安装包发布资源编辑工具。

## 9. 分阶段落地计划

### P0：数据模型 + 资源编辑工具夹名与修订

**范围**

- 扩展 `NoteConfig`／`NoteEntry`／读写与迁移。
- 夹名解析、60 警告／80 禁止、相关提示文案。
- 修订列表在工具内可查看；摘要可手改；保存／上页路径写入 `revisions`（自动摘要可先占位）。
- 上页预演与索引写入带上新字段（即使网站尚未展示）。

**验收标准**

1. 旧夹仅含 `modifiedAt` 时间戳时可被打开、迁移为 `revisions` 且不丢时间。
2. 夹名 `甲——乙` 解析为主「甲」、副「乙」；无破折号时副标题为空且可上页。
3. 夹名长度 60 字级警告、80 字级无法保存；主标题为空无法保存。
4. 单元测试在 YuePC（或约定的桌面测试环境）通过；不破坏现有配图上页用例。

### P1：网站展示

**范围**

- `NoteRecord`／`NoteCard`／`NoteDetailPage`：主副标题、创建与最近修改一行、点击展开修订列表。
- 列表页默认仍只显示创建日。
- 兼容缺字段旧索引。

**验收标准**

1. 详情页可见创建与最近修改；点击最近修改可展开完整列表（含摘要或占位）。
2. 有副标题时主副层次清晰；无副标题时不出现空白副标题行。
3. 列表页卡片日期语义仍为创建日；排序不变。
4. 前端相关测试通过。

### P2：自动摘要接入秘书／助手

**范围**

- 在保存或显著编辑时，由秘书协调助手根据内容 diff 生成中文短说明，写入 `revisions[].summary`（`source: "assistant"`）。
- 失败降级策略与可观测日志；用户仍可在工具里改摘要。
- Git 提交信息可选用同一文案，但网页不依赖 Git。

**验收标准**

1. 对有实质差异的保存，能得到非空短摘要的比例达到约定基线；失败时不阻断保存。
2. 用户手改后再次自动生成不得在无确认情况下静默覆盖（建议：已是 `source: "user"` 的条目不自动改写该条摘要；新编辑另起新条目）。
3. 端到端：改正文 → 自动摘要入库 → 上页 → 详情页展开可见。

**阶段协调**：秘书按 P0 → P1 → P2 推进；P0 完成后即可开 P1，不必等 P2。用户已说明本文落地后立刻开始实现，后续再提调整。

## 10. 风险与非目标

**风险**

- 夹名承载中文后，资源管理器、备份工具、部分脚本若假设夹名仅为时间戳，可能出问题；需排查硬编码 `yyyyMMdd_HHmmss` 的路径逻辑，改为「任意夹名 + `正文.md` 判定」。
- 标题与正文一级标题不一致时，读者可能看到正文里还有一个旧 H1；上页已有 `WithoutFirstHeading`，需确认发布稿与中转站预览行为是否都符合预期。
- 助手摘要质量不稳：必须可手改，且失败不阻断。
- 长度按字符计数在中英文混合时观感不同；阈值 60／80 可能需日后微调（见可调项）。

**非目标（本计划明确不做）**

- 不把中文夹名当作对象存储（例如腾讯云对象存储）的对象键。
- 不把整段 Git 历史无筛选地展示到网页。
- 不强制把 slug 改成可读英文单词；不要求为每篇手写语义化 slug（沿用现有 `n-时间` 规则即可，除非用户另提）。
- 不在本阶段重做整站信息架构或心得栏目视觉大改版（仅细节页时间行与标题层次所需的最小样式）。
- 不把修订摘要系统扩展到其他栏目（摄影、手绘等），除非另立项。

## 11. 待用户后续可调项

以下项本计划给出默认建议，用户可随时改口而不推翻主架构：

1. 列表卡片是否额外显示「近改」日期或小徽标。
2. 无修订时详情页「最近修改」是隐藏还是与创建相同。
3. 长度阈值是否从 60／80 调整（例如 50／70 或按显示宽度估算）。
4. 是否允许用户删除某条修订，或仅允许改摘要。
5. 多个 `——` 时是否改为禁止并提示，而不是「右侧整段作副标题」。
6. 是否对用户误输入的 `--`、`—`（单字符 U+2014）做自动纠正为 `——`。
7. 新建心得是先时间戳夹名再改名，还是创建对话框一次收齐主副标题。
8. 助手自动摘要的语气、最大字数、以及是否在摘要中提及配图变更。
9. 索引 `version` 是否在本次必升到 `2`。
10. 详情页时间精度（到日／到分钟／到秒）与时区文案（站点面向访客时是否标注「北京时间」等）。
